# Safety Rules

## 1. Core Safety Policy

**SAFE → execute automatically.**
**UNSAFE / DESTRUCTIVE → ask for explicit user approval first.**

Always ask before:

- destructive or irreversible operations;
- production data/infrastructure changes;
- database data/schema changes;
- database migrations;
- Git commit/push/history rewriting;
- full supplier imports;
- bulk product updates/deletes;
- destructive Docker cleanup;
- bulk external-service operations.

## 2. Git

Never automatically:

- `git commit`
- `git push`
- `git push --force`
- `git reset --hard`
- rewrite Git history.

Safe read-only Git commands are allowed:

- `git status`
- `git diff`
- `git log`
- `git show`

If a commit/push would be appropriate, ask first.

## 3. Command Execution — Destructive

Ask before commands that may delete data, overwrite important data, alter system
configuration, modify production, or cause irreversible changes:

- `rm`, `rm -rf`
- `docker system prune`
- `docker volume rm`
- `docker compose down -v`
- destructive SQL
- destructive database operations
- destructive `sudo`
- firewall/SSH/user-permission changes
- production infrastructure changes.

## 4. Production Protection

Treat production as sensitive.

Before any operation that can modify data or infrastructure:

1. Determine the target environment.
2. Verify the actual service/database/container involved.
3. If the environment is unclear, ask first.

Never automatically:

- delete/reset production data;
- delete production databases or volumes;
- run destructive production migrations;
- remove production media;
- modify production infrastructure;
- deploy to production;
- restart/rebuild production infrastructure destructively.

## 5. Database Safety

### Automatically allowed

- read-only SQL;
- schema inspection;
- checking tables, columns, indexes, constraints, and foreign keys;
- test queries;
- inspecting database state.

Development database changes are allowed automatically **only when clearly
non-destructive, idempotent, and required by the task**.

### Approval required

Ask before:

- `DROP`, `TRUNCATE`, mass `DELETE`;
- destructive `UPDATE`;
- database reset/deletion;
- volume deletion;
- destructive data migrations;
- schema-changing SQL;
- production data changes;
- bulk updates with uncertain impact.

Never delete existing production data merely to make a migration/import succeed.

## 6. Migration Safety

Creating a migration file and executing it are separate operations.

**Always ask for approval before executing:**

- `alembic upgrade`
- `alembic downgrade`
- `alembic stamp`
- `alembic revision --autogenerate`
- any schema/data-changing SQL.

Never execute an autogenerated migration without reviewing it.

Never assume Alembic history and the actual schema are identical.

Always distinguish:
A. editing an existing migration
B. creating a new migration
C. executing a migration
D. stamping Alembic history
E. manually modifying the database.

Detailed migration workflow is in `database-migrations` skill.

## 7. Supplier Import Safety

Supplier imports may modify large amounts of catalog data.

Never automatically:

- run a full supplier import;
- run a full production import;
- perform bulk product updates/deletes;
- delete products merely because they are absent from a supplier feed.

Prefer:

- dry-run;
- parsing;
- validation;
- statistics;
- preview;
- test fixtures.

A real full import requires explicit user approval.

## 8. Docker Safety

Before modifying Docker configuration, inspect:

- `docker-compose.yml`;
- relevant Dockerfiles;
- environment configuration;
- service dependencies.

Automatically allowed:

- `docker compose ps`
- `docker compose logs`
- `docker inspect`
- normal image builds;
- normal development container recreation when required.

Ask before:

- `docker compose down -v`;
- removing volumes;
- deleting potentially important containers/images;
- `docker system prune`;
- any destructive cleanup.

Never remove database volumes merely to solve a development problem.

## 9. Authentication & Security

Never expose secrets.

Never:

- commit `.env`;
- hardcode production credentials;
- expose API keys unnecessarily;
- put secrets in `NEXT_PUBLIC_*`;
- expose `BREVO_API_KEY` to frontend code;
- log passwords;
- log raw auth/reset tokens.

Use environment configuration for:

- API keys;
- database credentials;
- SMTP/Brevo credentials;
- secret keys;
- production URLs;
- environment-specific settings.

`.env.example` may contain placeholders only.

Authentication changes must preserve:

- password hashing;
- token hashing;
- expiration;
- session invalidation;
- email verification;
- password reset security;
- rate limiting.

Run relevant tests after authentication changes.

## 10. External Services Safety

For services such as Brevo:

- never use fake credentials;
- never expose API keys;
- avoid bulk real-world operations during testing;
- prefer one controlled test email;
- require approval for bulk email operations.

When credentials are unavailable, test the integration structurally and explicitly
state that real delivery was not verified.
