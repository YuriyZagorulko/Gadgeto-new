# Migration Plan — from WordPress/WooCommerce to the New Store

The strategy is **staged, reversible, and non-destructive** to the legacy systems.
Phases from the task spec (§28) are reflected below as concrete steps.

---

## 0. Guiding rules

1. WordPress stays the production system until the new store is explicitly approved.
2. Every pre-step gets a backup (DB, media, config). Rollback is restored from backup.
3. All migration logic is code (Alembic + migration scripts) in this repo — the
   production DB is never hand-edited.
4. The final mapping JSONs and the backup tar are reference data — never modified.

## 3. Data migration scope (verified in the audit)

**Definitely migrating:**
- Categories (188) incl. tree order + orphan duplicates reconciled
- Products (≈22.5k; publish/private/trash semantics; images via stored files or
  preserved URLs)
- Product attributes (`pa_*` values, ~4k terms) + attribute taxonomies (196)
- Product–category and product–attribute relations
- Prices, old prices, stock status, SKUs, brands
- Descriptions/short descriptions, meta supplier_slug/supplier_sku
- Final mapping sets (195 + 1,119 + 186 + 395 + remove lists)
- Category-specific filters (187)
- Category SEO (187) + product SEO meta (`_yoast_*`)
- URLs & sitemap inventory (to map 301s)

**Being created fresh (not migrated):**
- users (6 legacy accounts are re-created manually; passwords not migrated)
- orders (12 rows, 11 trash/test — not worth migrating; record as reference only)
- carts/sessions
- payments/shared keys (new env-provided credentials)

### 3.1 Product linkage matrix

| WP/WooCommerce | New table |
|---|---|
| `wp_posts.product` + `_*` postmeta | `products` (goods columns + is_visible/is_active derived from publish/private + `_visibility`) |
| `post_name` slug | `products.slug` (byte-for-byte) |
| `_thumbnail_id`, gallery, uploads files | `product_images` (+ files to storage) |
| `term_relationships` → `product_cat` | `product_categories` |
| `pa_*` terms | `product_attributes` (attribute_value_id) |
| `product_brand` | `brands` / joined via `attributes` (dedupe with `Бренди`) |
| `supplier_slug`/`supplier_sku` | product supplier linkage; a `manual` supplier for `mine` items |
| `_yoast_*` | products.seo_* |
| `wc_orders` | archived import only (rows to `orders` if strictly required) |

## 4. Mapping migration (from JSON → PostgreSQL)

Per `DATA_MAPPING.md §3`: archive JSON into `mapping_sources`, then populate
`supplier_*`, `category_mappings`, `attribute_mappings`,
`attribute_value_mappings`; apply the `is_removed` flags; import
`woocommerce_categories.json` seeds and `CategoriesSEO_Final.json` SEO rows.
Verification checklist in `DATA_MAPPING.md §8`.

## 5. URL / SEO migration

- Keep product slugs byte-for-byte (percent-encoded) → `/products/{slug}` route
  (or `/shop/{slug}` alias). Decide the canonical internal path; write `/shop/*`
  → new path 301 via `url_aliases`.
- Category slugs unchanged → path `/category/{slug}`; orphan variants (parent 0)
  get 301 to the canonical tree node.
- Sitemap/robots regenerated by the new backend (same coverage as Yoast).
- Title/description templates ported from the legacy SEO generator.

## 6. Verification (Definition of Done for migration)

- `alembic upgrade head` from clean DB passes migration tests.
- Same product set as WC export (count ± tolerable drift; sample-check hashes,
  prices, categories).
- Spot-check: 20 random products in new store match source fields
  (name/sku/price/stock/category/attrs/SEO/image count).
- All mapping counts verified (see Data Mapping §8).
- Category filters: Laptops+Monitors (sample) show right filters; default categories
  get the global fallback.
- Search: uk/ru/en queries work.

## 6. Backups + rollback

- Before Phases 3,5,9: dump new DB; keep legacy untouched.
- Rollback = restore the previous dump (remediation run documented in
  `DEPLOYMENT.md`), keep WordPress running until cutover approved.
