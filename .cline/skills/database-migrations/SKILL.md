# Database Migrations Skill

## Overview

Database schema changes are managed through Alembic. Migrations are located in
`migrations/versions/`. The Alembic configuration is at `backend/Alembic.ini`.

**Safety constraint**: Creating a migration file and executing it are separate
operations. Executing migrations always requires explicit approval (see
`01-safety.md`).

## Migration Files

Migrations are at: `migrations/versions/`

Naming convention: `NNN_descriptive_name.py`

Current head revision: **033_channel_exports**

## Historical Migrations — Immutable

Once a migration exists, treat it as immutable. Do not modify:

- SQL in `upgrade()` / `downgrade()`;
- revision identifiers;
- dependencies;
- behavior.

Prefer a **new migration** for new schema changes.

## Workflow

### Before creating a migration

Inspect:

1. Current Alembic revision: `alembic current`
2. `alembic_version` in the database
3. Migration history: `alembic history`
4. Actual database schema
5. Relevant SQLAlchemy models (in `backend/app/models/`)
6. Existing migrations affecting the same tables

Never assume Alembic history and the actual schema are identical.

### Creating a new migration

```bash
cd backend
alembic revision --autogenerate -m "description"
```

**Always review autogenerated migrations before executing them.**

When reviewing autogenerate output:

- inspect the entire migration;
- verify all `CREATE/ALTER/DROP` statements;
- remove unrelated changes;
- verify indexes, constraints, foreign keys, nullable/default behavior, and enum changes.

### Schema consistency checks

- All migrations should be idempotent.
- `alembic upgrade head` from an empty DB must work cleanly.

### If an old migration appears to require modification

STOP and ask. Report:

1. migration involved;
2. why it appears necessary;
3. whether it is already applied;
4. whether its schema changes already exist in the database;
5. safer alternatives (e.g., a new migration).

## Execution

Before executing an approved migration, report:

- filename;
- revision;
- down revision;
- exact schema changes;
- expected database impact.

After execution, verify:

- Alembic revision matches expected;
- affected schema matches expected;
- application starts and responds;
- relevant tests pass.

## Distinguish These Operations

| Operation | Description |
|-----------|-------------|
| A. Editing an existing migration | Modifying a historical migration file |
| B. Creating a new migration | Writing a new revision file |
| C. Executing a migration | Running `alembic upgrade` |
| D. Stamping Alembic history | Setting revision without running migrations |
| E. Manually modifying the database | Direct SQL changes outside Alembic |

Never execute an autogenerated migration without reviewing it.
